# Proposal（v1.0）

## 決策摘要

- 選了把單一活動組別上限由 12 提高至 50／代價是老師端清單與結果表必須容納更多列／可被 50 組無法完整操作的驗收證偽。
- 選了沿用既有 `POST /api/teacher/teams` 與 `activity-lifecycle` 能力／代價是契約與主規格必須同步修訂／可被出現第二套大班 API 或近義規格證偽。
- 選了維持預設 4 組、每組最多 6 台及既有階段、撤銷、隔離與順位規則／代價是 50 組組隊時最多承載 300 台／可被既有行為回歸、容量探針或 50 組並發順位失敗證偽。
- 選了以自動驗收、容量探針與人工 UI 紀錄共同判定／代價是增加測試與驗證工時／可被矩陣缺落點或負例不會轉紅證偽。

## Why

現行單一活動只允許 2–12 組，無法支援負責人指定的大班分組情境。依 2026-11-27 指示，本卡將上限提高至 50，並確保擴容不改變作答隔離、公平判定與活動階段同步。

## What Changes

- 老師在 `preparing` 階段可設定 2–50 組；預設仍為 4 組，非整數與範圍外輸入回 422，其他階段仍回 409。
- 老師端與學生端須可完整呈現與操作第 1 組至第 50 組；50 組下的選組、釋放、組隊與結果檢視維持既有語意。
- 50 組、每組最多 6 台時，既有組別憑證、邀請碼、WebSocket 狀態裁切與答案隔離仍成立；容量探針驗證最多 300 台的本機情境。
- 修改 `contracts/api.md` 的 `{count}` 範圍，並在 `eval/acceptance/matrix.yaml` 新增 `team-limit-50` 的 API、隔離、容量與 UI 落點。
- 涵蓋需求：R-01、R-11；同時回歸 R-09、R-10 與 team-mode 的每組 6 台限制。
- parity：已登記 `docs/parity.md:40`「`team-limit-50`」及 `docs/parity.md:73`「2026-11-27」變更紀錄，實作後兩 repo 的共用程式、契約與矩陣須逐項對齊。

### 本卡不做

- 不提高每組 6 台裝置上限，不改預設 4 組。
- 不改活動階段、憑證撤銷、邀請碼、作答隔離、搶答順位、計分或揭曉規則。
- 不新增分頁、搜尋、虛擬捲動或對外部署；若人工驗證證明 50 組不可操作，另立有主人的 UX 卡。

## Capabilities

### New Capabilities

無。

### Modified Capabilities

- `activity-lifecycle`：將老師可設定的組數由 2–12 改為 2–50，並明定邊界、非法輸入與 50 組狀態同步行為。

## Impact

- API 契約：`contracts/api.md:32`「`POST /api/teacher/teams`」。
- 伺服器：組數常數、輸入驗證、組別狀態與既有身分／隔離路徑。
- Web：老師端組數輸入上限、50 組清單與結果表的可操作性及窄畫面捲動。
- 驗收：server API／階段／隔離／組隊回歸、web 元件測試、300 台容量探針、人工 UI 紀錄與 `make gate`。
- 依賴：不新增第三方套件或外部服務；容量判斷取決於本機執行結果，必須在提案期保留探針與原樣輸出。
